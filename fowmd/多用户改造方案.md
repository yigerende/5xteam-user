# 多用户改造方案

## 背景与目标

本系统目前是单管理员模式：`app_users` 表只有一行 `admin`，登录会话不记录身份（`sessions` 是 `map[token]过期时间`，不含用户名），所有数据表都没有归属列。数据库里已有 100 个 Free 账号、128 个 OpenAI 账号、144 条空间进入历史，正式环境已运行数月，通过本地推 GitHub、生产端拉取重建 Docker 的方式更新。

目标：

1. 支持多用户登录，每个用户看到和使用的界面功能完全一致。
2. 仅 `admin` 账号可见「用户管理」菜单，对用户增删改查。
3. 每个用户的数据完全独立——账号、母号、代理、推送配置、历史、额度监控互不可见、互不干扰。
4. 现网数据零丢失，升级即拉取即用，不需要手工迁移步骤。

## 现状评估：为什么这不是一个小改动

必须先说清工作量，因为它决定了实施方式。

**数据层**：24 张表，其中 5 张是 `id INTEGER PRIMARY KEY CHECK (id = 1)` 的全局单例配置表（`settings`、`sub2_settings`、`cpa_settings`、`pro_settings`、`auto_rotation_settings`）。SQLite 无法 `DROP CONSTRAINT`，这 5 张表以及 5 处单列 `UNIQUE`（`proxies.name`、`admin_accounts.label`、`openai_accounts.label`、`mail_accounts.email`、`free_accounts.user_id`）都必须重建表，不能只 `ADD COLUMN`。

**调用面**：`internal/httpapi` 里有 448 处 `s.store.*` 调用，其中 `Settings()` 一处就有 42 个调用点。`Store` 有 129 个导出方法。134 条路由中 50 条带 `{id}`/`{email}` 路径参数，每一条都需要归属校验。

**隐性泄漏点**：这是最危险的部分。多处跨表聚合按**邮箱或上游 user_id** 关联，而不是按记录 id，加归属列时如果只改外层查询、不改 JOIN 两侧，数据会静默串号：

- `populateAdminCurrentSpace`（store.go:937）无条件扫全表 `free_accounts`，把子号邮箱按 `AdminAccountID` 归到母号卡片上。
- `reconcileAdminTeamRotationChildCounts`（store.go:982）同样全表扫，而且**会写回** `UPDATE admin_accounts SET profile=?`——跨用户读会把污染的计数永久写进母号档案。
- `mailAccountPageCTE`（pagination.go:62）三表 JOIN 全部以邮箱为键，`visits` 子查询 `SELECT email,COUNT(DISTINCT team_id) FROM team_visits GROUP BY email` 决定另一个用户邮箱行上显示的 `space_state` 和 `visited_team_count`。
- `HasVisitedTeam`（team_history.go:135）是业务逻辑而非展示：它决定账号能否再次进入某个 Team。不隔离的话，A 用户的历史会挡住 B 用户的进入。
- `syncTeamHistory`（team_history.go:58）一个函数里四处泄漏，其中包括 `admin.TeamRotationChildCount++` 写别人的母号计数。

**命名陷阱**：`free_accounts.user_id`、`team_visits.user_id`、`account_progress.user_id` 里的 `user_id` 指的是**上游 ChatGPT 用户 id**，不是本系统用户。归属列绝对不能叫 `user_id`，否则后续维护必然出错。本方案统一用 `owner`。

**后台 worker**：5 个常驻 goroutine（`monitorFreeAccounts`、`autoRotationLoop`、`monitorProAccounts`、`monitorHeroActivations`、`autoRotationHistoryCleanup`）都读全局单例配置、遍历全表记录，且运行在没有请求上下文的环境里——拿不到"当前用户"。这是架构上最需要决策的一块。

**进程级单例**：`autoRunning`、`proMonitorRunning`、`planCheckNext`、`seatAssignmentMu`、`oauthProxyActive` 都是全局的。`autoRunning` 尤其关键——它现在的语义是"全系统同时只跑一轮自动轮转"，多用户下会变成 A 用户跑轮转时 B 用户的轮转被跳过。

**已确认不成问题的部分**（避免实施时做无用改造）：

- `sub2.Client`/`cpa.Client` 虽然被所有用户共享，但 Sub2 的登录 token 缓存以 `URL+Email+密码` 的 SHA-256 为 key（sub2/client.go:505），配置不同会自动重新登录。共享实例是安全的，只是两个用户配置不同时会互相失效缓存，多一次登录开销。
- OAuth Python 子进程不落盘任何账号数据，全部通过 stdin/stdout 传递（`protocol_codex_oauth.py`）。Node 的 Sentinel SDK 缓存按版本命名、只读。并发 OAuth 天然隔离，不需要处理临时文件冲突。
- 加密主密钥是进程级单一密钥，AAD 为 `nil`。多用户下继续用同一把密钥即可，不需要改动加密层（代价是密文在行之间是可移植的，但这不构成新的风险面，因为数据库本身就是可信边界内的）。

## 关键决策：后台 worker 与全局资源的语义

在动手前必须定下这几条，否则实施到一半会卡住。本方案的选择如下。

**1. 每用户独立配置，worker 按用户循环。**  
5 张单例配置表加 `owner` 进主键，每个用户一份自己的接口设置、推送设置、轮转设置。worker 的循环改为「取出所有用户 → 对每个用户读他自己的配置 → 只遍历他自己的账号」。这是唯一能满足"数据完全独立"的做法：如果配置共享，A 用户改了推送线路会立刻影响 B 用户的所有账号。

**2. `autoRunning` 等进程单例改为按用户维度。**  
`autoRunning bool` → `autoRunning map[string]bool`（owner → 是否在跑）。`proMonitorRunning`、`planCheckNext` 同理。`seatAssignmentMu` 保持全局即可——它保护的是席位分配的临界区，持有时间极短，全局串行不会成为瓶颈。

**3. 母号/Team 级的锁保持全局。**  
`teamRemoveLocks` 按 Team account id（上游 id）加锁。**必须保持全局**：如果两个用户恰好配置了同一个母号（现实中会发生，比如共用一批母号资源），OpenAI 的 per-Team 限流是按上游 Team 算的，按用户分开加锁反而会触发 429。这一条是刻意不做隔离。

**4. `turb` 回调按 Basic Auth 用户名归属。**  
`/api/integrations/turb/register` 绕过 session、用 HTTP Basic 认证。它已经调 `CheckUserPassword(username, password)`，所以把该 username 作为导入数据的 owner 即可，无需新增参数。这意味着每个用户配自己的 `REMOTE_IMPORT_PASSWORD` 就能把账号导入自己的空间。

**5. 共享资源池的归属：接码号池按用户隔离。**  
`sms_phones`/`sms_phone_bindings` 加 `owner`。理由是卡密是花钱买的、绑定次数有上限，跨用户共享会导致互相消耗额度。`sms_platform_configs` 同样按用户（每个用户填自己的平台密钥）。

**6. 全局清理操作保持全局。**  
`PurgeAutoRotationHistory`（48 小时）、`RecoverAutoRotationClaims`、`RecoverSMSActivations`、`ProOAuthSession` 过期清理属于进程生命周期操作，继续全局执行。但 `ClearHistory`（清空执行历史）和 `AddHistory` 的 100 条上限必须改为按用户，否则一个用户清历史会清掉所有人的。

## 实施方案

### 第一阶段：数据层加归属（风险最高，需最谨慎）

**新增 owner 列的统一约定**：列名 `owner TEXT NOT NULL DEFAULT ''`，沿用仓库既有的 `ensureOpenAIRefreshColumn`（store.go:795）风格——`PRAGMA table_info` 探测 + `ALTER TABLE ADD COLUMN`，同时在 `initSchema` 的 `CREATE TABLE` 里也声明该列，让新库直接建出来、老库走 ALTER 路径。

**需要重建表的 10 张**（无法用 ADD COLUMN 解决约束问题）：

| 表 | 原约束 | 改为 |
|---|---|---|
| `settings` | `CHECK (id = 1)` | `PRIMARY KEY(owner)` |
| `sub2_settings` | `CHECK (id = 1)` | `PRIMARY KEY(owner)` |
| `cpa_settings` | `CHECK (id = 1)` | `PRIMARY KEY(owner)` |
| `pro_settings` | `CHECK (id = 1)` | `PRIMARY KEY(owner)` |
| `auto_rotation_settings` | `CHECK (id=1)` | `PRIMARY KEY(owner)` |
| `proxies` | `name NOCASE UNIQUE` | `UNIQUE(owner,name)` |
| `admin_accounts` | `label NOCASE UNIQUE` | `UNIQUE(owner,label)` |
| `openai_accounts` | `label NOCASE UNIQUE` | `UNIQUE(owner,label)` |
| `mail_accounts` | `email NOCASE UNIQUE` | `UNIQUE(owner,email)` |
| `free_accounts` | `user_id UNIQUE` | `UNIQUE(owner,user_id)` |

重建流程放在一个事务里：建新表（带 owner 和复合约束）→ `INSERT INTO 新表 SELECT *, 'admin' FROM 旧表` → `DROP` 旧表 → `RENAME`。重建期间 `PRAGMA foreign_keys` 本来就没有实际外键声明，不需要额外处理。

**只需 ADD COLUMN 的表**：`mail_messages`、`sms_phones`、`sms_activations`、`history`、`account_progress`、`auto_rotation_runs/tasks/events/claims/seat_reservations`、`admin_capacity_snapshots`、`pro_oauth_sessions`、`team_visits`、`team_cycles`、`sms_platform_configs`、`sms_phone_bindings`。其中 `team_visits` 的 `PRIMARY KEY(user_id,team_id)` 和 `UNIQUE(email,team_id)`、`account_progress` 的 `PRIMARY KEY(team_account_id,user_id)`、`sms_phone_bindings` 的 `PRIMARY KEY(phone_id,gpt_email)`、`admin_capacity_snapshots` 和 `auto_rotation_claims` 的单列主键，也都需要把 owner 纳入主键 → 这些同样要重建。实施时以「约束是否需要变」而非「是否要加列」来判断走哪条路。

**数据回填**：现网所有数据归属 `admin`。回填就是重建时 `SELECT *, 'admin'`，以及 ADD COLUMN 后一条 `UPDATE 表 SET owner='admin' WHERE owner=''`。因为默认值是 `''` 而不是 `'admin'`，可以用 `owner=''` 精确识别「升级前的老数据」，回填幂等、可重跑。

**`app_users` 表扩展**：加 `role TEXT NOT NULL DEFAULT 'user'`、`created_at TEXT`、`enabled INTEGER NOT NULL DEFAULT 1`。现有 admin 行回填 `role='admin'`。密码哈希沿用现有的 12 万轮 SHA-256 迭代（auth.go:13），不改算法——改算法会导致现有密码失效。

**Store 方法签名改造**：129 个方法中约 95 个需要 owner 参数。建议做法是引入一个轻量包装：

```go
// Scoped 把 owner 绑定到一次调用序列上，避免在 448 个调用点逐个传参。
type Scoped struct {
    store *Store
    owner string
}
func (s *Store) For(owner string) *Scoped
```

这样 `s.store.FreeAccounts()` 变成 `s.scoped(r).FreeAccounts()`，handler 里从 session 取 owner 一次。相比给 129 个方法逐个加参数，这个方式改动点集中、编译器能帮忙查漏（`Scoped` 上不提供未改造的方法，漏改的地方直接编译失败）。

**跨表聚合的修复清单**（必须逐个处理，这是静默泄漏的根源）：

**Store 方法签名改造**：129 个方法中约 95 个需要 owner 参数。有两种做法：

*做法 A——直接加参数*：`FreeAccounts()` → `FreeAccounts(owner string)`。改动点多（448 处调用），但编译器会把每一处漏改都报出来，不存在"忘了传"的静默错误。

*做法 B——包装类型*：给 `Store` 加一个 `Scoped(owner)` 方法返回绑定了 owner 的视图，handler 里用 `s.scoped(r).FreeAccounts()`。调用点改动小，但需要为 95 个方法写一遍转发代码，且新增方法时容易忘记加进视图。

**本方案推荐做法 A**。理由：这是一次性的大改造，编译期全覆盖检查比少敲几个字重要得多。漏传 owner 的后果是数据串号——正是这次改造要消灭的问题，不能依赖人工核对。

配套动作：把归属校验收敛到读取路径。`FreeAccountCredential(owner, id)`、`MailAccountCredential(owner, email)`、`AdminAccountCredential(owner, id)` 这些按 id/email 取单条的方法，一律在 SQL 里带上 `AND owner=?`，查不到就返回「不存在」而不是「无权访问」——这样 50 条带路径参数的路由自动获得越权保护，不需要在每个 handler 里单独写检查。

**必须逐个修改的跨表聚合**（前文列出的隐性泄漏点，这是最容易漏的一环）：

- `populateAdminCurrentSpace`、`reconcileAdminTeamRotationChildCounts`：`SELECT profile FROM free_accounts` 加 `WHERE owner=?`。
- `mailAccountPageCTE`：`pipeline_sources`、`visits`、`mail_dead` 三个子查询各自加 `WHERE owner=?`，不只是外层。
- `FreeAccountsPage` 的 `mail_dead` CTE 和 `PendingSeatsByAdmin`：同上。
- `HasVisitedTeam`、`TeamVisits`、`syncTeamHistory`、`ReviewTeamHistory`：`(user_id=? OR email=?)` 全部追加 `AND owner=?`。
- `AdminCapacitySnapshots`、`SMSAccountID`、`OAuthSMSPhone`、`HasProxyURL`、`AddSMSPhone` 去重、`sms_phone_bindings` 的单绑定检查：加 owner 条件。
- `AddHistory` 的 100 条裁剪、`ClearHistory`：加 `WHERE owner=?`。
- 50 个/50 个的代理数与母号数上限：改为按用户计数。

**注意 SQLite 单连接约束**：`db.SetMaxOpenConns(1)`（store.go:65），多处方法有注释说明「SELECT 的 rows 必须先关闭再在同连接上写」。给 owner 加子查询时不要在未关闭的 rows 循环内做写操作，否则会在单连接上死锁。

### 第二阶段：会话携带身份

`sessions map[string]time.Time` → `map[string]session`，其中 `session{owner string; role string; expires time.Time}`。

- `createSession(owner, role)` 写入身份。
- `validSession` 改为返回 `(session, bool)`，中间件把 owner 放进 request context。
- `me` 返回真实的 `{username, role}`，替换现在硬编码的 `map[string]string{"username": "admin"}`（auth.go:102）。
- `changePassword` 用 session 里的 owner，替换硬编码的 `ChangeUserPassword("admin", ...)`（auth.go:124）——这是现存 bug，任何用户改密码都会改到 admin。
- 密码修改后不再清空全部 session，只清该用户自己的（现在 `s.sessions = make(...)` 会踢掉所有人，auth.go:129）。
- 顺手补一个 session 过期清理 goroutine：现在过期条目只在下次访问该 token 时才删除，长跑进程里会无界增长。

**并发登录性能提示**：`CheckUserPassword` 在持有 `s.mu` 的情况下跑 12 万轮 SHA-256（auth.go:44），配合单 SQLite 连接，多用户同时登录会串行排队。用户数在几十以内可接受；若担心，把哈希计算移到锁外（先查出 salt 和 hash，释放锁，再比较）。

### 第三阶段：后台 worker 按用户循环

5 个 worker 的改造模式统一为：

```go
for _, owner := range s.store.Usernames() {
    settings, _, err := s.store.Sub2Settings(owner)   // 每个用户自己的配置
    if err != nil || !settings.QuotaEnabled { continue }
    accounts := s.store.FreeAccounts(owner)           // 只遍历自己的账号
    // ……原有逻辑不变
}
```

进程单例改为按 owner 的 map：`autoRunning map[string]bool`、`proMonitorRunning map[string]bool`、`planCheckNext map[string]time.Time`。`autoMu`/`proMonitorMu` 继续保护这些 map。

`teamRemoveLocks`、`seatAssignmentMu` 保持全局（见前文决策 3）。

`invokeFreeHandler`（auto_rotation.go:896）用 `httptest` 复用 handler，必须把 owner 注入到伪造 request 的 context 里，否则自动轮转会拿不到身份。

### 第四阶段：归属校验（防越权）

50 条带 `{id}`/`{email}` 的路由，每条在取记录后校验 `record.Owner == 当前用户`，不匹配返回 404（不用 403——避免泄漏"该 id 存在"这个信息）。

最稳妥的落法是让单记录读方法自带 owner 条件（`WHERE id=? AND owner=?`，见第一阶段），这样查不到就自然是 404，不依赖 handler 逐个写校验、也不会漏。

### 第五阶段：用户管理接口与界面

**接口**（全部要求 `role=admin`，中间件统一拦截）：

```
GET    /api/users            列表（分页，返回 username/role/enabled/created_at）
POST   /api/users            新建（username/password/role）
PUT    /api/users/{username} 改 role/enabled
POST   /api/users/{username}/password  管理员重置密码（不需要原密码）
DELETE /api/users/{username} 删除
```

约束：不允许删除或降级最后一个 admin；不允许删除自己；删除用户时一并删除其所有数据（按 owner 级联删除，需要覆盖全部 24 张表——建议实现成一个 `DeleteOwnerData(owner)` 事务方法，避免遗漏）。密码最少 6 位，与现有 `ChangeUserPassword` 规则一致。

**前端**（`frontend/src`）：

- `App.vue:21` 的 `nav` 数组改为 `computed`，`isAdmin` 为真时追加 `{ id: 'users', label: '用户管理', icon: Users, group: '系统' }`。注意 `nav[0]`（第 59 行）和 `nav.find`（第 60 行）要跟着改成 `nav.value[...]`。桌面端和移动端两处 `v-for="item in nav"`（139、142 行）因此自动生效，不用改模板。
- `checkAuth`（118 行）现在把 `/api/auth/me` 的返回**丢掉了**，改为存进 `me` ref 并派生 `isAdmin`。`onAuthenticated`（122 行）也要重新拉一次 `me`——登录接口的返回同样是被丢弃的。
- 视图渲染在 `SettingsView` 之后加 `<UsersView v-if="isAdmin && current === 'users'" />`。`v-if` 里必须带 `isAdmin`，因为 `current` 是从 localStorage 恢复的（33 行），被降权的用户否则会直接渲染该页面。同时应在拿到身份后校正一次 `current`，避免它停在一个已不可见的 tab 上（`activeNav` 会静默回退到 `nav[0]`，导致面包屑显示错误）。
- 新建 `components/UsersView.vue`，直接照 `ProxiesView.vue` 的骨架改：`form` 单个 reactive（`form.id` 为空即新建模式）、`setMessage` 反馈、`loadPage` 分页三件套、`form.id ? PUT : POST` 的保存分支、`window.confirm` 删除确认。复用 `MessageBar`、`Pagination`、`StatusPill`、`IconButton`，样式类沿用 `.view-stack`/`.page-heading`/`.management-grid`/`.editor-panel`/`.list-panel`/`.field`/`.table-shell`/`.row-actions`。不要引入 Tailwind 工具类堆砌，与现有 house style 不符。
- `LoginView.vue:7` 把预填的 `'admin'`/`'admin'` 清空。
- `api.js` 加一个 401 回调钩子（`error.status` 已经带了状态码但全项目没人读），让 session 过期时自动回到登录页，而不是停在应用里反复报「未登录」。

### 第六阶段：验证

```powershell
gofmt -l internal/ cmd/
go vet ./...
go test ./...
cd frontend; npm run check; npm run build
```

**现有 115 个测试全部直接调 `store.Open(t.TempDir())` + `New(store, ...)`**，不带 owner。改造后这些测试需要统一注入一个默认 owner。建议在 `test_helpers_test.go` 里加一个 `newTestOwner(t, st)` 辅助函数，集中处理，避免改 115 处。

新增测试至少覆盖：

- 老库升级：用改造前的 `state.db` 副本启动，断言全部记录 `owner='admin'`、数量与升级前一致。
- 数据隔离：两个用户各建同名代理/同名母号/同一邮箱账号，互不冲突且互不可见。
- 越权：用户 A 拿 B 的记录 id 调 50 条路由中的代表性几条，全部返回 404。
- `HasVisitedTeam` 隔离：A 用户进过某 Team 不影响 B 用户进入同一 Team。
- worker 隔离：A 用户关闭额度监控不影响 B 用户的监控继续运行。
- 用户管理：不能删最后一个 admin、不能删自己、删除用户会清空其全部数据。
- 权限：普通用户访问 `/api/users` 全部返回 403。

## 上线步骤（配合现有 GitHub → Docker 流程）

1. 本地跑完第六阶段的全部验证。
2. **备份生产数据**：停容器后备份 `state.db`、`state.db-wal`、`state.db-shm` 和 `.master-key`。三个 db 文件要一起备份（WAL 模式下缺 WAL 会丢最近写入）；`.master-key` 丢了所有加密凭据无法解密。
3. 推 GitHub，生产端 `git pull`。
4. `docker compose build --no-cache && docker compose up -d` —— 依赖和 Dockerfile 没变的话可以不加 `--no-cache`，但本次改了 Go 代码，重新 build 是必须的。
5. 首次启动时自动完成表重建与回填。**观察启动日志**，确认迁移无报错——迁移失败会导致 `store.Open` 返回错误、进程直接退出（cmd/server/main.go:26 的 `fatal`），此时用备份回滚。
6. 用原 admin 密码登录，逐页确认数据完整（100 个 Free 账号、128 个 OpenAI 账号、2 个代理、1 个母号）。
7. 在用户管理里建第二个用户，登录确认它看到的是空数据、且能独立配置。

**回滚**：停容器 → 恢复备份的四个文件 → `git checkout` 回上一个 commit → 重新 build。因为迁移会重建表，**旧版本二进制无法读取新库结构**，所以回滚必须同时回滚代码和数据文件，不能只回代码。这一点务必在操作前确认备份可用。

## 工作量与风险

改动规模：约 95 个 Store 方法、448 个调用点、134 条路由、5 个后台 worker、24 张表的结构迁移，前端约 6 个文件。这是一次涉及全部数据表和全部业务路径的结构性改造，不是增量功能。

**最高风险项**，按优先级：

1. **跨表聚合的静默泄漏**。这类 bug 不会报错、不会崩，只会让用户看到别人的数据或被别人的历史挡住操作。前文清单里的每一项都必须逐个改并测到。
2. **表重建的数据完整性**。10 张以上的表要 DROP + RENAME，任何一处 `SELECT *` 列顺序出错都会错位。建议每张表重建后立刻断言行数一致。
3. **回滚不可逆性**。迁移后旧二进制读不了新库，必须靠文件备份回滚。

**建议的推进方式**：分阶段提交、分阶段上线。第一、二阶段（数据层 + 会话身份）可以先上线并保持只有 admin 一个用户——此时行为与现在完全一致，能验证迁移正确性而不改变任何业务语义。确认稳定后再上第三到五阶段（worker 隔离 + 用户管理）。这样把「迁移风险」和「多用户逻辑风险」分开暴露，出问题时容易定位。
